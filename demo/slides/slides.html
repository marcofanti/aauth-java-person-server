01 · Why
Agents need authority.
API keys are the wrong shape for it.
An autonomous agent acting for a person needs credentials that are scoped to a purpose, approved by a human, and revocable — not a long-lived key that grants everything forever.

Identity

Agents hold Ed25519 keys, not passwords. An Agent Server binds those keys to a human-approved identity and vouches for them with short-lived aa-agent+jwt tokens.

Authority

A Person Server brokers access on the person's behalf: every grant is tied to a declared mission, and anything unusual escalates to the person for consent.

Audit

Evaluator verdicts, consents, denials, and agent-reported actions land in one mission log — the person can always answer “what did my agent do, and who said yes?”

04 · Method
The Python server is the spec
Wire parity beats Java idiom. Anything a client can observe is identical — the Java server is a drop-in replacement, proven by running the reference clients against it unchanged.

Identical on the wire

  • Routes, status codes (202 deferred flows, 401 challenges), error bodies
  • Env vars: AAUTH_PS_* · AAUTH_AS_* · AAUTH_DATABASE_URL
  • JWT claim shapes, pending/consent semantics, canonical mission bytes
  • Python walkthrough scripts pass unchanged, both security modes

Java under the hood

  • Immutable records with withers; sealed interfaces for outcome unions
  • Exhaustive switches over every protocol outcome
  • Thread-safe stores under Tomcat's pool (vs. Python's single-threaded loop)
  • Every deviation recorded in docs/PROGRESS.md

06 · Flow
Missions and brokered consent

The mission is a contract

A human-readable description plus the tools the agent intends to use. Its identity is s256 = SHA-256(exact response bytes) — agent, server, and console all reference the same bytes.

POST /token { resource_token,
  justification, mission }
→ 202 { requirement: interaction,
  code, interaction_url,
  pending_url }

The consent moment

The person opens /ui/consent.html?code=… and sees the mission, the justification, the requested scopes, and the evaluator's note — then approves, denies, answers a question, or asks the agent to clarify. The agent's next poll gets the verdict: an aa-auth+jwt bound to its key (cnf.jkt), or a clean refusal.

07 · Governance
Two layers, default-deny

Layer 1 — mission evaluator

Every token request is judged against the mission and its history. The keyword evaluator ships four crisp verdicts:

allow  scope matches the mission
escalate  unsure → ask the person
clarify  ask the agent first
deny  mission forbids it

Layer 2 — approved tools

POST /permission gates individual actions: tools named in the mission are granted instantly; anything else — a credit-card charge, say — defers through the same pending/consent machinery, and a denial comes back as a first-class, auditable outcome.

Swap the keyword evaluator for an LLM or policy engine via MissionEvaluator — the interface is one method.

Everything lands in the mission log: evaluator verdicts, consents, denials, and agent-reported POST /audit entries — one trail per mission hash.

09 · Operations
Modes and persistence

Security modes

  • Secure (production shape) — RFC 9421 verification, scheme=jwt on POST /token, real Ed25519-signed aa-auth+jwt
  • Insecure-dev (demos, localhost only) — signatures parsed, not verified; stub agent identity; fake federated tokens
  • Same routes, flows, and UI in both — the demo runs insecure so plain curl + openssl can play the agent

State

  • In-memory by default — fresh on every start, ideal for demos and tests
  • Set AAUTH_DATABASE_URL — SQLite for local dev, PostgreSQL for real deployments; one shared ps_* / as_* schema
  • Restart-survival tested — missions, bindings, pending requests, and issued-token records come back after a restart
